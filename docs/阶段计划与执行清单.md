# 阶段计划与执行清单

> 文档状态：执行版 v0.3（2026-09-07）。P1 S0 最小闭环已完成，P2 正式问题集和公平对照待开始。
>
> 本文件是本组的执行清单。要求、项目目标和每阶段验收证据分别记录在[课程要求](./课程要求.md)、[项目章程与开发路线](./项目章程与路线.md)和本文件中。

## 1. 总体目标

本项目最终交付一个能够从公开文本构建知识图谱、执行 Vector/Graph/Hybrid 检索、生成带证据答案，并用统一数据和统一模型进行公平比较的 GraphRAG 系统。

最终结论必须由可复现实验支持：

- 哪些问题类型适合 Vector RAG、GraphRAG 或 Hybrid RAG。
- 图结构是否真正提高了多实体、多跳和全局问题的证据覆盖与答案质量。
- 图谱构建错误、实体重复、关系误抽取和检索配置如何影响结果。
- GraphRAG 的额外索引成本、查询延迟、LLM 调用量和估算费用。
- 系统在哪些问题上失败，以及后续改进是否在固定评测集上真实有效。

不预设 GraphRAG 必然优于 Vector RAG；如果没有提升，也要如实报告适用边界和失败原因。

## 2. 研发优先级

## 2.1 已确认的实现方向

- 正式范围固定为两个标准 benchmark（GraphRAG-Bench Novel、GraphRAG-Bench Medical）和一个实际应用场景 Enron Email；具体来源、版本和准入条件见[Enron 实际应用方案](./实际应用领域方案.md)。
- Enron Email 使用规模足够大的开放邮件语料，设计 20–30 道跨邮件自建问题，并选取 3–5 个代表性案例用于课堂展示和失败分析；《红楼梦》保留为早期候选记录，不进入当前最终应用主线。
- HotpotQA、MuSiQue、2WikiMultiHopQA 等多跳 QA 数据集暂列备用/参考，不进入当前正式结果，除非后续明确扩大范围。
- 生成和图谱抽取优先使用 DeepSeek API，不部署或训练本地语言模型。
- GraphRAG 的生成模型和 embedding 模型分开配置。生成使用 DeepSeek V4 Flash API，embedding 使用本地 `Qwen/Qwen3-Embedding-0.6B`；本地 embedding 通过跨平台服务/适配层接入，不部署本地语言模型。
- 建库和查询必须读取同一套 embedding 配置：模型 ID、revision、设备、dtype、输出维度、归一化、pooling 和批量策略都要一致。
- 运行环境覆盖 macOS 和 Windows。脚本优先使用 Python/uv、相对路径和 `.env` 环境变量，不依赖 macOS 或 Windows 特有 shell 命令。

本组暂不在本文件设计成员分工或汇报材料结构，相关内容在进入阶段汇报准备时单独登记。

### 第一优先级：可靠评测体系

先固定数据、问题、答案依据、模型、embedding、提示词和资源预算，再比较 Vector、Graph 和 Hybrid。所有改进都必须回到同一评测集重新运行，不能用更换数据或模型制造提升。

### 第二优先级：图谱质量

重点审计实体规范化、实体去重、关系准确性、关系方向、别名处理、证据文本绑定和孤立节点。图的边数不是质量指标；含义不清的 `related_to` 不能替代有定义、有证据的关系。

### 第三优先级：检索质量

按顺序比较 Vector only、Graph only、Vector + Graph 和 Vector + Graph + reranker。先确认检索证据是否正确，再调 prompt；不能把生成模型的偶然发挥误认为图检索收益。

### 第四优先级：本组自己的测试

上游测试已按适用性清理，但本组必须重新建立小而稳定的测试体系：代码检查 → 单元测试 → 集成测试 → 端到端 smoke test。测试应验证本项目自己的数据格式、索引产物、检索证据和引用链路。

### 第五优先级：可见证据与展示

最终展示要能从一个问题展开：问题 → 匹配实体 → 图路径/子图 → 文本证据 → 答案 → 引用，并同时展示 Vector 与 GraphRAG 的差异、成功案例和失败案例。

## 4. 固定评测问题集

第一版内部 pilot 目标为 30 题，每类至少 5 题，用于验证字段、检索链路和评测脚本。正式评测分为两种：GraphRAG-Bench 使用官方问题、参考答案和官方评测协议；Enron 实际应用场景设计 20–30 道跨邮件问题，并人工登记标准答案、原文证据、实体、关系/路径和预期是否需要图结构。六类问题是本组实际应用问题的设计框架，不应被误写成 GraphRAG-Bench 的官方题型定义。

| 类别 | 目的 | 最低要求 | 重点指标 |
|---|---|---:|---|
| A. 单事实问题 | 检查基本事实召回和生成准确性 | 5 题 | 答案正确性、ROUGE-L、延迟 |
| B. 多实体关联问题 | 检查多个实体在同一答案中的关联 | 5 题 | Evidence Recall、实体召回、忠实度 |
| C. 多跳推理问题 | 检查跨文档或跨关系路径 | 5 题 | Multi-hop Success Rate、Path Recall |
| D. 全局总结问题 | 检查社区级信息聚合能力 | 5 题 | Coverage、忠实度、上下文相关性 |
| E. 图结构帮助有限问题 | 检查 GraphRAG 是否增加不必要成本 | 5 题 | 质量差异、延迟、成本、失败率 |
| F. 幻觉风险问题 | 检查无证据、歧义或错误前提下的拒答与引用 | 5 题 | 忠实度、证据支持率、拒答正确性 |

多跳题必须保存显式路径，例如：

```text
A 人 --participated_in--> Project X
Project X --led_by--> B 人
B 人 --graduated_from--> University Y
```

不能只保存最终答案而不保存中间实体和关系，否则无法计算 Path Recall，也无法解释 GraphRAG 为什么成功或失败。

## 5. 公平对照协议

Vector RAG、GraphRAG 和 Hybrid RAG 必须在同一份原始数据和同一批问题上运行，并尽量固定：

- LLM 名称、版本、temperature、最大输出长度和回答格式。
- embedding 模型、版本和向量距离算法。
- 原文清洗、chunk 大小、overlap 和问题顺序。
- 评测模型、重试次数、并发上限和上下文 token 预算。
- ground truth、证据标注和结果汇总脚本。

每次实验都要同时记录上下文长度、LLM 调用次数、输入/输出 token、索引时间、查询延迟和估算成本。后续增加 reranker 时，必须作为新实验条件登记，不能覆盖原始基线。

## 6. 图谱质量门禁

P4 之后至少完成一次人工抽样审计，审计表包含：

- 实体规范化：别名、缩写、不同语言写法是否合并正确。
- 实体类型：人物、组织、地点、作品、项目等类型是否稳定。
- 关系准确性：关系名称、方向、起止实体和时间信息是否有原文依据。
- 关系可解释性：避免用无语义的泛化关系代替具体关系。
- 证据绑定：每个关键实体/关系能否回溯到 source document 和 text unit。
- 图结构：重复实体率、孤立节点率、节点/边数量、社区数量和连通性。

在完成标注抽样前不设定虚假的质量分数目标；先形成可复核的标注集，再依据实际错误分布制定阈值。

## 7. 本组测试体系

### 7.1 单元测试

覆盖数据解析、字段校验、实体规范化、关系方向、路径计算、指标计算和结果 schema。单元测试不调用真实外部 LLM。

### 7.2 集成测试

使用临时目录和固定小样例，验证文档→切分→图谱/向量索引→检索产物之间的接口。优先使用可替换的 fake provider，避免 CI 依赖个人密钥。

### 7.3 端到端 smoke test

使用 5–20 篇小文档，完成：

```text
原始数据 → index → build graph → query → 非空答案 → 引用存在 → 预期实体至少被召回
```

这个测试只判断 pipeline 是否完整和证据链是否存在，不把“答案足够聪明”作为唯一通过条件。需要真实模型的 e2e 实验另行登记，不把密钥写入 GitHub 仓库。

## 9. 变更与验收规则

每个阶段结束时必须更新：

1. 目的：为什么做、解决什么风险。
2. 完成：代码、数据、配置、文档和结果有哪些变化。
3. 验证：执行了什么命令，结果是否通过，仍有哪些限制。
4. 进度：对应哪一阶段，距离老师评分项还差什么。
5. 下一步：下一项具体工作、前置条件和产物。

如果实验改进没有在固定问题集上重复验证，不得写成“效果提升”；如果 GraphRAG 只在部分问题类型有效，应把适用边界作为正式结果保存。
