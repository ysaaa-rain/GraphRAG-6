上述资产不是要求一次性全部纳入正式实验，而是形成多案例候选池。正式实验只使用完成准入记录、许可核验、版本固定和哈希登记的资产。

## 1.1 案例组合策略

为了避免只用《红楼梦》得出片面结论，正式路线至少覆盖以下四类材料：

1. **统一 benchmark**：GraphRAG-Bench Novel，必要时加入 Medical。
2. **中文实际案例**：《红楼梦》作为首个中文案例，再从 CText、维基文库等合法来源扩展其他作品或人物主题。
3. **多跳 QA benchmark**：HotpotQA、MuSiQue、2WikiMultiHopQA 中选择许可和字段适配最清晰的子集。
4. **结构化关系案例**：Wikidata 或 OpenAlex，验证实体别名、机构/作者/作品关系和跨文档路径。

医学开放文献只作为审慎的补充案例，不在未完成许可证和内容风险审核前用于最终结论。每个案例都要分别报告数据规模、图谱规模、问题类型、许可证和失败边界，不能把不同数据集的分数直接混成一个平均数。

## 2. 数据准入记录

每份数据必须有一条登记记录，至少包含：

- 数据名称、用途和所属实验。
- 原始来源 URL、发布组织和下载日期。
- 数据集版本、文件名、大小和 SHA-256 哈希。
- 许可证或使用条款，以及是否允许再分发。
- 文档数量、字符/token 数、语言、领域和预计图谱规模。
- 清洗、去重、切分、实体规范化和过滤规则。
- 可能的隐私、医学、版权、偏见或提示注入风险。
- 对应的 Git commit、配置和实验 ID。

## 3. 数据规模策略

“数据量上来”不能只等于下载大文件。本组采用三级数据规模：

1. S0 最小样例：几十 KB，用于代码和格式验证。
2. S1 小规模实验：GraphRAG-Bench Novel 100 题或少量文档，用于参数和失败分析。
3. S2 正式规模：Novel 全量、选定的多跳 QA 子集、多个中文/结构化案例和必要的 Medical 补充，用于正式结论。

每一级都要记录图谱节点、边、社区、文本 chunk 和 embedding 数量，才能判断 RAG 效果变化是否和数据规模有关。

## 4. 数据管理规则

- 原始数据和模型缓存默认放在 Git 忽略目录或外部存储，仓库只保留下载/校验脚本、元数据和必要的小样例。
- 不提交密钥、个人信息、未经许可的完整作品、模型缓存和大体积中间文件。
- 公开数据也不等于可以无限再分发；许可未确认时只保存来源链接和哈希，不把原文复制进远程仓库。
- 任何预处理都要可重复，不能只保留人工修改后的最终文件。
