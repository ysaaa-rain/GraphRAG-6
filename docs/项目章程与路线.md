# 项目章程与开发路线

> 文档性质：本文件是本组的执行章程。若后续组内确认主题或资源发生变化，应在这里更新，并同步更新评测与数据文档。

## 0. 项目主题

项目主题为：**基于知识图谱的 RAG 系统构建**。

## 1. 项目定位

本项目要构建一个能够解释 GraphRAG 工作过程、复现实验结果并支持 Vector/Graph/Hybrid 对照的知识问答系统。系统面向公开文本知识，输出答案时尽量保留证据来源和检索路径，便于老师理解、成员协作和后续调优。

## 2. 研究问题

核心问题不是“如何让 GraphRAG 看起来更复杂”，而是：

> 在什么类型的问题和数据结构下，显式实体—关系图能为 RAG 提供向量相似度之外的有效信息？这种收益是否足以抵消图谱构建、索引和查询带来的额外成本？

围绕这个问题，项目至少回答：

1. 对单跳事实问题，GraphRAG 是否会退化或保持稳定？
2. 对跨文档、多跳、全局主题问题，GraphRAG 是否提高证据覆盖和答案正确性？
3. Hybrid 是否比纯 Vector 或纯 Graph 更稳定？
4. GraphRAG 的收益来自图结构本身，还是来自更多 token、更多 LLM 调用或更好的提示词？
5. 图谱质量、检索配置、LLM 和数据规模分别对结果有什么影响？

## 3. 初版系统范围

### 必须完成

- 文本输入与切分。
- 实体、关系和必要的社区结构构建。
- 向量检索、图增强检索和混合检索至少各有可运行路径。
- LLM 知识注入与答案生成。
- 统一 benchmark 批量推理。
- Vector/Graph/Hybrid 结果、成本、延迟和失败样例的可追溯记录。
- 中文项目文档、测试和阶段性 Git 记录。
- 满足阶段 1 评分要求的 3–5 个代表性问题、数据处理前后样例和成员/进度说明。

### 暂不承诺

- 不在第一阶段追求自研图数据库或复杂前端。
- 不在没有实验数据之前声称 GraphRAG 必然优于 Vector RAG。
- 不把大规模原始数据、密钥、模型缓存或临时输出直接提交进 Git。

## 4. 目标与验收口径

### 工程目标

- 新成员可以按照文档完成环境准备、数据准备、索引、问答和评测。
- 任一结果都能追溯到代码 commit、配置、数据版本、模型、问题集和评测脚本。
- 每次合并都有测试或实验依据，文档描述与当前代码一致。

### 实验目标

首轮目标是建立可信对照，而不是预设胜负：

- 在 GraphRAG-Bench 上完成 Vector、Graph、Hybrid 三条可重复实验链路。
- 正式 benchmark 固定为 GraphRAG-Bench Novel 和 Medical；实际应用固定为 Enron Email 一个组织邮件场景。
- Enron 使用规模足够大的开放邮件语料、20–30 道本组跨邮件问题和 3–5 个最终展示案例；正式数据集到此停止扩展，后续投入深度而不是继续增加领域。
- 以复杂推理、上下文摘要和证据覆盖作为 GraphRAG 的重点观察指标。
- 以事实检索、延迟、LLM 调用量和估算成本作为稳定性与代价指标。
- 暂定优化目标：复杂推理或摘要主指标相对 Vector 基线取得至少 5% 的相对改善，同时事实检索不出现超过 2 个百分点的回退；该目标是本组的工程目标，不是预先写好的实验结论。

### 结果判定

若未达到优化目标，不修改数据或指标来制造提升，而是：

1. 按问题类型和数据规模分析失败。
2. 检查图谱质量和证据召回。
3. 报告 GraphRAG 的适用边界、额外成本和下一步改进。

## 7. 正式数据范围说明

当前正式范围已经确定为：

1. GraphRAG-Bench Novel：标准化的小说领域 benchmark。
2. GraphRAG-Bench Medical：标准化的医学领域 benchmark。
3. Enron Email 实际应用场景：从大规模组织邮件中构建人员、部门、项目、事件和主题关系图，强调跨邮件、多人物、多事件关联。

三个正式数据的知识结构已经形成差异：Novel 是叙事型隐含关系，Medical 是专业知识和决策链，Enron 是大规模跨邮件组织关系。老师课件中的《红楼梦》是教学示例，不作为当前最终应用主线。HotpotQA、MuSiQue、2WikiMultiHopQA 仅作为备用/参考资产，暂不纳入正式结果。
