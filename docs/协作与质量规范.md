# 协作与质量规范

## 1. 分支

- `main`：可演示、可复现、经过检查的稳定版本。
- `feat/<name>`：功能开发。
- `exp/<name>`：实验和调参，不直接视为稳定结论。
- `docs/<name>`：文档整理。
- `fix/<name>`：缺陷修复。

任何影响正式结果的实验必须在结果中记录代码 commit，不能只写“最新代码”。

## 2. Commit 规范

采用：`type(scope): 目的`，例如：

- `docs(course): 整理课程要求与检查表`
- `chore(baseline): 导入并固定基线版本`
- `feat(eval): 增加统一结果格式`
- `exp(vector): 记录向量检索基线`
- `fix(index): 修复实体合并边界条件`

一个 commit 尽量只解决一个可描述的问题。commit 说明至少回答“为什么改、改了什么、如何验证”。

## 3. 合并前检查

合并前由提交者完成：

1. 查看 `git diff`，确认没有密钥、聊天记录、临时文件或无关改动。
2. 运行与改动相关的单元测试、静态检查和最小端到端测试。
3. 检查文档中的命令、路径、参数与当前代码一致。
4. 对结果类改动保存运行配置、数据版本、模型版本和原始输出路径。
5. 在变更记录中补充目的、进度、验证结果和下一步。

## 4. AI 辅助编程质量门禁

AI 生成的代码不能直接视为正确。必须经过：

- 人工读懂控制流、输入输出、异常处理和依赖。
- 小样例运行和边界用例测试。
- 代码格式、静态检查和现有测试。
- 对生成的中间文件进行清理或加入明确的 Git 忽略规则。
- 在合并说明中写清已知限制，答辩时能解释关键实现。

## 5. 文档同步

代码、配置、实验结果和文档属于同一个交付物。以下变更必须同步文档：

- 改变命令、目录、配置字段或环境要求。
- 改变检索逻辑、评测指标或输出格式。
- 增加/删除数据集、模型或实验结果。
- 修复影响结果的 bug。

文档不记录聊天上下文或内部推理过程，只记录对项目理解、复现、协作和验收有用的信息。

## 6. 阶段性进度汇报格式

每次重要开发或实验结束后，在变更记录中用同样的顺序写清楚：

1. 目的：这次工作要解决什么问题，为什么现在做。
2. 完成：修改了哪些文件、接口、配置或数据。
3. 验证：运行了什么命令，结果是什么，是否还有已知问题。
4. 进度：对应项目路线的哪个阶段，距离验收还差什么。
5. 下一步：下一项具体动作、前置条件和预计产物。
